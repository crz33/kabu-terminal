# アイデアの検証

投資の見立てを 1 つ受け取り、効いたかどうかを数字で確かめて `kessannote` に残す。
成果物は 3 つで、名前を揃える。

| 成果物 | 置き場 | 役割 |
| --- | --- | --- |
| 出し方 | `kessannote/methods/<名前>-v<版>.md` | 要素の定義と母集団。版で固定する |
| SQL | `kessannote/analysis/<名前>-v<版>.sql` | 断面と検証を 1 本で出す |
| レポート | `kessannote/reports/YYYYMMDD_<名前>-v<版>.md` | 何が効いて何が効かなかったか |

**定義を変えたら版を上げ、3 つとも新しく作る。** 古い版は触らない。同じ版をデータが増えて
流し直したときだけ、レポートを上書きする。

先例は競馬式 (`keiba-v1`)。SQL の骨組みはそこから写す。

## 前提

```bash
cd kabu-app
set -a && . ./.env && set +a
export PGURL="${DATABASE_URL#postgresql+psycopg://}"
psql "postgresql://$PGURL" -A -F' | ' -v dates='<時点をカンマ区切り>' -f ../kessannote/analysis/<名前>-v<版>.sql
```

`DATABASE_URL` にはパスワードが入っている。`echo` しない。

## 手順

### 1. 要素に分解して、保有期間を決める

アイデアを 2〜3 個の要素に割る。要素ごとに「何を測りたいか」を 1 行で書き、それを DB の
どの列で代用するかを表にする。**保有期間を最初に決める。** オッズや地合いの指標は期間で
変わる。1 四半期なら次の決算まで、という具合に区切りを言葉にしておく。

期間で読みが分かれるときはユーザに聞く。それ以外は自分で決めて表に書く。

### 2. データの穴を先に確かめる

定義を書く前に、上場銘柄のうち何銘柄でその値が取れるかを数える。

```sql
SELECT count(DISTINCT d.code) FROM tdnet_disclosures d JOIN tdnet_summary_facts f ON f.doc_id=d.doc_id
JOIN stocks s ON s.code=d.code AND s.is_listed
WHERE d.disclosed_date >= current_date - 400 AND f.concept = '<要素名>';
```

3000 を切る項目は、平均に入れるときに NULL を除く設計にする。1000 を切る項目は要素に
しない。

**時点ごとの断面は「その時点で読めた書類」だけで組む。** 短信は `disclosed_date <= 時点`、
有報は `financials.available_at <= 時点`。後から出た数字を混ぜると、検証が嘘になる。

### 3. 出し方を書く

`kessannote/methods/<名前>-v1.md` に、要素の対応表、母集団、値の取り方、順位の付け方、
効きの測り方、流し方を書く。frontmatter は `kind: analysis`。

### 4. SQL を書く

`kessannote/analysis/<名前>-v1.sql` を 1 本で書く。形は決まっている。

1. `dates` を受けて時点 (`asof`) と次の時点 (`fwd`) の組を作る。最後の時点は `ticks` の最新日まで
2. 時点ごとの断面を `CREATE TEMP TABLE` に落とす。列は要素の生値と順位、先行リターン
3. 検証の表を `\echo` で区切って並べる

守ること。

- **順位は `percent_rank()` で 0〜1 にし、高いほど良い向きに揃える。** NULL は
  `PARTITION BY asof, (x IS NULL)` で順位から外し、`CASE WHEN x IS NOT NULL` で NULL に戻す
- **複数要素を束ねるときは NULL を除いた平均。** `coalesce` で 0 にすると、取れない銘柄が
  最下位に沈む
- **株価は `coalesce(adjusted_close, close)`。** 過去の `adjusted_close` は 8 割が NULL だが、
  分割の無い銘柄なので `close` と同じ値になる。分割のあった銘柄は夜間バッチが埋めている。
  自前で飛びから分割を推定しないこと。実際の暴落を分割と誤認して 20% 以上ずれた行が出た
- **株式数と 1 株あたりの値は開示時点の株数で書かれている。** 開示日から時点までの分割は、
  両日の `adjusted_close / close` の比で直す。`keiba-v1.sql` の `sp` を写す
- **大きな中間表は CTE でなく `TEMP TABLE` にしてインデックスを張る。** CTE に対する LATERAL
  の `max()` は毎回全走査になり、10 分経っても返らない
- `round()` は `::numeric` を付ける。`percent_rank` は double を返す
- 時点が最新日と同じ行は先行リターンを NULL にする。0% として検証に混ざる

### 5. 効きを測る

最低限これだけ出す。**中央値を主に読む。** 少数の急騰が平均を引っ張る。

- 合成スコアの 5 分位ごとの先行リターン (時点別と束ねたもの)
- 要素ごとの上位 20% − 下位 20% の差。合成より単独が強ければ、混ぜたぶん薄まっている
- 同じ差を時点別に。全体の中央値を添え、地合いで効きが変わるかを見る
- 同じ差を市場区分別に。小型株の癖でないかを見る
- 時価総額 3 分位 × スコア 5 分位

要素が 2 つなら中央値で割った 2×2 も出す。見立てが「A が高くて B が低いものを避ける」の
ような形なら、その象限が実際に低いかで判定できる。

### 6. 書く

`kessannote/CLAUDE.md` の書き方に従う。frontmatter は `type: analysis`、`method: <名前>-v1`。
`summary` には**何が効いて何が効かなかったか**を書く。手法の紹介ではない。

節の順は、母集団 → 合成スコアの分位 → 要素ごと → 時点別 → 区分と時価総額 → 今日の断面 →
次に試すこと → 未確定。

**効かなかった要素で選ばれた上位銘柄を、買う候補として書かない。** 今日の断面を載せる
ときは、検証の結果と併せて「この上位を買う根拠は無い」まで書く。

**「次に試すこと」は次の版の案として書く。** 要素ごとに v1 と v2 の案を表で並べ、置き換える
理由を 1 行ずつ付ける。会話で出た案を箇条書きで溜めるだけにしない。次の版はこの表から
始める。

レポートの冒頭には 3 要素に何を使ったかの表を置く。定義は `methods/` にあるが、読む人は
レポートから開くので、要約が無いと表の意味が取れない。

### 7. 建てて commit する

```bash
cd kessannote && npx astro build && npx astro check
```

出し方・SQL・レポートを 1 つのコミットに入れる。**push はしない。** ユーザが指示するまで待つ。

## ここからが本番

レポートを出したら、ユーザが結果を読んで「なぜ」と「次は」を出してくる。1 問ごとにこの順で回す。

1. **まず用語と定義を答える。** 「q5 とは」「中央値の % は何の数字か」「能力に何を使ったか」
   から始まる。レポートに書いてあるかを確かめ、無ければ本文に足す
2. **仮説が出たら層別で確かめる。** 「織り込み済みでは」なら開示後の騰落で割る。「予想は
   信用できないのでは」なら予想と実績の達成率を出す。「分母に予想を入れるのがまずいのでは」
   なら分母を替えて効きを比べる。推測で答えず、40 秒で出るなら出す
3. **結果をレポートに書き戻し、SQL に同じ節を足す。** 会話で出した数字がレポートに無い、が
   一番まずい。時点別の表を文で済ませていたら表にする
4. 読みが変わったら `summary` と「次に試すこと」を直す。未確定は解けたものを外し、掘って
   出た問いを足す

**ユーザの指摘で自分の読みが覆ったら、はっきり撤回して書き換える。** 「予想の信頼性が低い」
と書いて、達成率を出したら中央値が 102% だった。予想は正しく、分布の裾が偏っていただけ。
撤回した読みはレポートに残さない。

**同じ日のうちの訂正は版を上げない。** 分割の扱いを変えて数字が小数点以下で動いたときは
v1 のまま直した。push 前で、結論が変わらないうちは訂正でよい。翌日以降や、結論が動く
変更は v2 にする。

**混ぜる前に単独で見る。** v1 は先に合成してから要素ごとの効きを出したので、効かない要素が
合成を薄め、重なる要素 (PER と PBR) が二重に効いた。次の版は単独の効きと要素どうしの
順位の相関を先に出し、効いたものだけを合成する。

## つまずきどころ

**発行済株式数は `tdnet_summary_facts` にある。** 上場銘柄の 99% で取れる。自己株式数、
予想 EPS、BPS、ROE もある。時価総額も予想 PER も出せる。

**表紙の要素名は会計基準で末尾が変わる。** `OperatingIncome` / `OperatingIncomeIFRS` /
`OperatingIncomeUS`。売上は `NetSales` `SalesIFRS` `OperatingRevenues` `Revenue` など
10 種類以上。正規表現でまとめて拾い、`is_consolidated DESC NULLS LAST` で連結を優先する。

**通期予想の `scope` は短信の種類で変わる。** 本決算の短信では `Next`、四半期では
`Current`。`fact_type = 'Forecast' AND period_kind = 'Year'` だけで絞れば両方拾える。

**四半期短信の `Prior` は前年同期であって前期通期ではない。** 前期の通期実績が要るなら本決算の
短信を引くか、表紙の「対前期増減率」を使う。

**`adjusted_close` の NULL は欠損ではない。** 調整後終値は分割だけを直した値で、分割の無い銘柄
では `close` と同じになる。分割のあった銘柄は夜間バッチが埋め済み。残りの NULL も 2026-09 から
1 晩 50 銘柄ずつ埋めていて、2026-12 頃に無くなる。それまでは `coalesce` で引く。

**会社予想はどこに入れても偏りを持ち込む。** 予想は概ね当たる (達成率の中央値 102%) が、
控えめな予想は上振れ、強気な予想は 3 社に 1 社が 10% 超で下振れる。株価はそのずれに反応する
ので、予想の水準を能力にすると逆に効き、予想 EPS を PER の分母にすると強気予想が「安い」側に
紛れる。実績 PER (+4.73) と PBR (+5.91) のほうが予想 PER (+4.28) より効いた。

**実績 EPS は本決算の短信にしか載らない。** 四半期短信の `Prior` は前年同期の値。時点以前の
最新の本決算 (`quarter = 'FY'`) を別に引いて `scope = 'Current'` の `Year` を取る。

**`ntile` に NULL を混ぜない。** `ORDER BY x` で NULL は最後に並び、上位の組に入る。
`PARTITION BY asof, x IS NULL` で分けてから切る。これを踏んで上位 20% が 49 行になった。

**temp テーブルを何本も足すと `no empty local buffer available` で落ちる。** psql を
`-c "SET temp_buffers='512MB'"` で始める。セッションで temp テーブルを触る前に設定すること。

**52 週高値からの下落率は「オッズ」にならなかった。** 1 四半期の保有では、深く下げた銘柄は
さらに下がる側にいた。逆張りの要素を入れるなら、保有期間を伸ばすか検証してから入れる。

**会社予想の増益率は能力にならなかった。** 予想が高い銘柄ほど先行リターンが低い。織り込みか
下方修正かは分けていない。能力は実績で測る方が筋がよい。
