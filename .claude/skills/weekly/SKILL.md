# 週次レポート

土曜に 1 週間の市況をまとめ、`kessannote/reports/` に置く。

数字は DB から出す。原因だけ Web で裏を取る。**裏が取れなかったものは断定せず「未確定」に
落とす。** 投資判断の土台になるので、出所の怪しい理由を書かないこと。

## 前提

| 対象 | 値 |
| --- | --- |
| レポートの置き場 | `kessannote/reports/YYYYMMDD_weekly-market.md` |
| SQL | `kessannote/analysis/weekly-market.sql` |
| DB 接続 | `kabu-app/.env` の `DATABASE_URL` (`kabu_dev`) |

```bash
cd kabu-app
set -a && . ./.env && set +a
export PGURL="${DATABASE_URL#postgresql+psycopg://}"
psql "postgresql://$PGURL" -A -F' | ' -v d0=<起点> -v d1=<終点> -f ../kessannote/analysis/weekly-market.sql
```

`DATABASE_URL` にはパスワードが入っている。`echo` しない。

## 手順

### 1. 株価が揃っているか確かめる

週次の株価取得は土曜 03:00 に走り、2 時間 20 分かかる。終わる前に書くと銘柄数が 1000 ほど
足りないまま集計してしまう。

```sql
SELECT max(date) AS 最新日,
       count(*) FILTER (WHERE date = (SELECT max(date) FROM ticks)) AS 最新日の銘柄数
FROM ticks;
```

最新日が直近の営業日で、銘柄数が 3600 台なら揃っている。3000 を切っていたら取得中か失敗して
いる。`status` スキルで確かめること。

### 2. 期間を決める

暦ではなく `ticks` にある日で決める。祝日があるため。

```sql
SELECT (SELECT max(date) FROM ticks) AS d1,
       (SELECT max(date) FROM ticks WHERE date <= (SELECT max(date) FROM ticks) - 7) AS d0;
```

`d0` が前週末の終値、`d1` が当週末の終値になる。

### 3. SQL を流す

`analysis/weekly-market.sql` をそのまま使う。毎週コピーしない。4 秒ほどで返る。出るのは 8 つ。

全体 / 市場区分別 / 業種別の騰落 / 日ごとの中央値 / 週ごとの売買代金 / 区分別の倍率 /
業種別の倍率 / 商いが膨らんだ銘柄。

### 4. 目立つ動きを拾う

拾うのはこの 4 つ。

- 中央値が最も低い業種と最も高い業種
- 区分のあいだで差がついたところ
- 売買代金の倍率が 1.5 を超えた業種と銘柄
- 指数と中央値がずれた日

**業種の倍率が跳ねていたら、まず中身が 1 銘柄でないかを見る。** 情報・通信業が 1.71 倍に
なった週は、ほぼソフトバンクグループ単独だった。

### 5. 原因を裏取りする

まず DB を引く。適時開示が出ていれば、それが答えになる。

```sql
SELECT disclosed_date, disclosed_time, title
FROM tdnet_disclosures WHERE code = '<コード>' ORDER BY disclosed_date DESC LIMIT 10;
```

集めているのは決算短信だけなので、業務提携などは入らない。DB に無ければ Web を引く。

**記事は必ず開いて、日付と中身を確かめてからリンクする。** 検索結果の要約は数字がずれる。

決算に触れるときは `latest_financials` から引く。記事の数字を写さない。

**初回は深追いしない。** 1 つの動きにつき、DB を 1 回と Web 検索を 2 回まで。そこで出典に
辿り着けなければ「未確定」に落として次へ進む。全部を潰そうとすると 1 本に何時間もかかる。
残したものは、ユーザが読んで気になったところから掘り下げる。

### 6. 書く

`kessannote/CLAUDE.md` の書き方に従う。frontmatter は `type: weekly`、`method:
weekly-market-v1`、`date` は作成日。`summary` には**結論**を書く。話題ではなく、何が
分かったかを書く。

**「出し方」の節に手順を書き写さない。** [`methods/weekly-market-v1.md`](../../../kessannote/methods/weekly-market-v1.md)
に書いてある。本文にはその週に固有の値だけ置く。期間、母集団の件数、いつもと違うことを
したときの断り。

定義を変えて数字が動いたら、版を上げて `methods/weekly-market-v2.md` を作る。既存の版は
書き換えない。古いレポートが古い版を指したままになるように。

分からなかったことは `## 未確定` に残す。`/open/` が全レポートから拾う。

### 7. 建てて commit する

```bash
cd kessannote && npx astro build && npx astro check
```

commit は `kessannote` で行う。レポートと SQL を同じコミットに入れる。

**push はしない。** ユーザが指示するまで待つ。ここから質問の往復が始まり、レポートが
何度か変わる。

## ここからが本番

レポートを出したら終わりではない。ユーザが読んで、銘柄や「未確定」について質問してくる。
**そこで調べた結果は、会話で答えて終わりにせず、必ずレポートに書き戻すこと。** 書き戻さ
ないと、次に同じ問いが来たときにまた調べ直すことになる。

### 8. 質問に答えて追記する

1 問ごとにこの順で回す。

1. **DB を先に引く。** 適時開示、決算、値動きの日別。答えが DB にあることは多い
2. 足りなければ Web を引く。記事は開いて日付と中身を確かめる
3. 数字が食い違ったら、その銘柄だけ取得元から取り直して照合する
4. レポートに節を足す。出典のリンクを必ず付ける
5. 建て直して commit する

会話の返答とレポートの中身を揃えること。会話では書いたのにレポートに無い、が一番まずい。

### 9. 未確定を動かす

質問で解けたものは「未確定」から外す。**代わりに、掘ってみて新しく出てきた問いを足す。**
未確定は減らすものではなく、入れ替わるもの。

部分的にしか解けなかったときは、消さずに文を書き換える。何が分かって何が残っているかを
書く。JPX の更新日は観測が 3 点に増えても特定できなかったので、「観測は 3 点に増えた。
ただし拡張子の変更と重なって切り分けられない」に書き換えた。

`date` は動かさない。同じ日の追記なら作成日のままでよい。日をまたいで大きく書き足した
ときだけ、最終更新日に寄せる。`summary` は結論が変わったら直す。

### 10. 指示が出たら push する

```bash
cd kessannote && git push origin main
```

`kabu-app` や `kabu-terminal` に触っていれば、それぞれ別に push する。

## つまずきどころ

**SQL を直したら、前と同じ数字が出るか照らすこと。** 動くかどうかだけ見ても足りない。
単位を十億と億で混ぜていたのを、全体の売買代金と突き合わせて見つけたことがある。

**検索結果の要約は数字がずれる。** ソフトバンクグループの 09-04 終値を「5,001 円」とする
要約が出たことがある。実際は 5,590 円だった。値は必ず `ticks` を正とする。

**記事の配信時刻を見る。** 前場引け (12:37 など) の記事は大引けと値が違う。09-07 の記事は
SBG を 6,052 円としているが、大引けは 6,217 円だった。食い違いに見えたら、まず時刻を疑う。

**出来高が少ない日を「動いていない」と読まない。** ストップ高やストップ安に張り付くと商いが
細る。ティアフォーは 08-31 に 194 万株で +20% 上げた。前後は 3,800 万株と 8,000 万株ある。

**指数が上げた日に中央値が動いていないことがある。** 09-07 は日経平均が前場で 2% 以上上げた
一方、中央値は 0.00% だった。値がさ 2 銘柄が指数を押し上げただけで、地合いは重かった。
等加重で見る意味がここに出るので、乖離を見つけたら書くこと。

**指数は持っていない。** 日経平均も TOPIX も Yahoo から取れない。手元の `ticks` から等加重で
作る。日経平均の騰落に触れるときは、必ず出典を付ける。
