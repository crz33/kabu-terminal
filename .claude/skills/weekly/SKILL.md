# 週次レポート

土曜に 1 週間の市況をまとめ、`kessannote/reports/` に置く。

数字は DB から出す。原因だけ Web で裏を取る。**裏が取れなかったものは断定せず「未確定」に
落とす。** 投資判断の土台になるので、出所の怪しい理由を書かないこと。

## 前提

| 対象 | 値 |
| --- | --- |
| レポートの置き場 | `kessannote/reports/YYYYMMDD_weekly-market.md` |
| SQL | `kessannote/analysis/weekly-market.sql` |
| DB 接続 | `kabu-app/.env` の `DATABASE_URL` (`kabu_dev`) |

```bash
cd kabu-app
set -a && . ./.env && set +a
export PGURL="${DATABASE_URL#postgresql+psycopg://}"
psql "postgresql://$PGURL" -A -F' | ' -v d0=<起点> -v d1=<終点> -f ../kessannote/analysis/weekly-market.sql
```

`DATABASE_URL` にはパスワードが入っている。`echo` しない。

## 自動実行

土曜 06:00 に kabu の cron が `bin/weekly-auto` を流し、手順 1〜7 を無人で回す。株価の取得と
同じロックが空くまで待ち、銘柄数が 3500 を切っていたら書かずに止める。結果も失敗も
`/var/tmp/kabu-notify/` に置き、IRIS がそれを Telegram に流す。ログは `journalctl -t kabu-weekly`。

Claude は `dontAsk` で動き、`bin/weekly-auto` の中で許可した道具しか使えない。DB は
`bin/kabu-psql` で繋ぐ。変数展開やコマンド置換を含むコマンドは許可のルールに当たらないので、
接続文字列はスクリプトの中で読む。手順を変えて新しいコマンドが要るようになったら、許可の
一覧に足して `bin/weekly-auto --dry` で通るか確かめること。

自動で書いたあとは、ユーザが読んで質問してくる (手順 8)。動画はつなげない。


### 1. 株価が揃っているか確かめる

週次の株価取得は土曜 03:00 に走り、2 時間 20 分かかる。終わる前に書くと銘柄数が 1000 ほど
足りないまま集計してしまう。

```sql
SELECT max(date) AS 最新日,
       count(*) FILTER (WHERE date = (SELECT max(date) FROM ticks)) AS 最新日の銘柄数
FROM ticks;
```

最新日が直近の営業日で、銘柄数が 3600 台なら揃っている。3000 を切っていたら取得中か失敗して
いる。`status` スキルで確かめること。

### 2. 期間を決める

暦ではなく `ticks` にある日で決める。祝日があるため。

```sql
SELECT (SELECT max(date) FROM ticks) AS d1,
       (SELECT max(date) FROM ticks WHERE date <= (SELECT max(date) FROM ticks) - 7) AS d0;
```

`d0` が前週末の終値、`d1` が当週末の終値になる。前々週末は SQL の中で同じ規則で決める。

### 3. SQL を流す

`analysis/weekly-market.sql` をそのまま使う。毎週コピーしない。20 秒ほどで返る。出るのは 10 個。

全体 (当週と前週) / 市場区分別 / 業種別の騰落と順位 / 日ごとの中央値 / 週ごとの売買代金 /
区分別の前週比と直前 4 週比 / 業種別の倍率 / 商いが膨らんだ銘柄 / 時価総額加重と中央値
(直近 12 週) / 当週の差と中央値が全期間の何番目か。区分・業種・売買代金には前週の列が付く。

系列は既定で 12 週分出る。全期間が要るときは `-v weeks=1000` を足す。

### 4. 目立つ動きを拾う

**軸は前週との比較。** 週の中のどの日に動いたかは内訳で、主役にしない。拾うのはこの 6 つ。

- 中央値と上昇した割合が前週からどう変わったか。急落や急騰の翌週なら、2 週を通した騰落も見る
- 業種の順位の入れ替わり。中央値が最も低い業種と最も高い業種
- 区分のあいだの差。前週から開いたか縮んだか
- 売買代金の前週比と直前 4 週比。直前 4 週比が 1.5 を超えた業種と銘柄。前週が特殊な週なら前週比は
  振れるので、直前 4 週比と並べて読む
- 指数と中央値がずれた日 (「日ごとの動き」にだけ書く)
- 時価総額加重と中央値の差。差の絶対値が 90% 点 (SQL の最後の出力にある。2026-11 時点で
  2.31 ポイント) を超えた週は、大型株だけが動いた週として節を立てる (手順 6)。日経平均との
  ずれがあっても、時価総額加重との差が小さければ値がさ株の特性であって、大型株全般の動きではない

**業種の倍率が跳ねていたら、まず中身が 1 銘柄でないかを見る。** 情報・通信業が 1.71 倍に
なった週は、ほぼソフトバンクグループ単独だった。

### 5. 原因を裏取りする

まず DB を引く。適時開示が出ていれば、それが答えになる。

```sql
SELECT disclosed_date, disclosed_time, title
FROM tdnet_disclosures WHERE code = '<コード>' ORDER BY disclosed_date DESC LIMIT 10;
```

集めているのは決算短信だけなので、業務提携などは入らない。短信が出ていたら、値動きの
理由は本文にある。`data/tdnet/<開示日YYYYMMDD>/<doc_id>.zip` の `qualitative.htm` を読む
(読み方は `CLAUDE.md` の「データとインフラ」)。特損や予想の修正は Web の記事より先に
ここで分かる。短信が無ければ Web を引く。

**記事は必ず開いて、日付と中身を確かめてからリンクする。** 検索結果の要約は数字がずれる。

決算に触れるときは `latest_financials` から引く。記事の数字を写さない。

**初回は深追いしない。** 1 つの動きにつき、DB を 1 回と Web 検索を 2 回まで。そこで出典に
辿り着けなければ「未確定」に落として次へ進む。全部を潰そうとすると 1 本に何時間もかかる。
残したものは、ユーザが読んで気になったところから掘り下げる。

### 6. 書く

`kessannote/CLAUDE.md` の書き方に従う。frontmatter は `type: weekly`、`method:
weekly-market-v3`、`date` は作成日。`summary` には**結論**を書く。話題ではなく、何が
分かったかを書く。前週と比べて何が変わったかで書く。

**`summary` は 3 文まで、150 字程度に収める。** 個別銘柄、金利、時価総額加重との差のような
節の中身は入れない。トップの一覧と Telegram の通知にそのまま出るので、流し読みできる長さに
する。本文の書き出しで `summary` を繰り返さない。本文は冒頭の表から始める。

節はこの順に置く。

1. 冒頭: 当週と前週を並べた表 (中央値、上昇した割合、10% 以上下げた銘柄、時価総額加重、差、
   日経平均の騰落と終値、売買代金の日平均) と、全期間での順位
2. 時価総額加重と中央値 (差が 90% 点を超えた週だけ)
3. 区分 (前週と 2 週の列)
4. 業種 (上位 5 と下位 5、順位と前週の順位)
5. 売買代金 (前週比と直前 4 週比)
6. 商いを膨らませた銘柄
7. 原因
8. 日ごとの動き (表と 1〜2 段落。日付で語る話はここに集める)
9. 出し方、未確定

**時価総額加重と中央値の節は、差が 90% 点を超えた週だけ立てる。** 全期間で年に 5 週ほど
しか点かない。点いた週は、直近の週の系列と寄与の大きい銘柄の表を置き、どの大型株が指数を
動かしたかを書く。点かない週は節を立てず、冒頭の表の直後の段落に「差は +X ポイントで 90% 点の
内側にある。大型株だけが動いた週ではない」の 1 文だけ書く。逆の「中小型だけが動いた週」は
2026-11 時点の 149 週で一度も点いていない。差が小さい週から言えることは中央値で足りる。

**日ごとの話は「日ごとの動き」にだけ書く。** 冒頭、区分、業種、原因に日ごとの表や「11-09 と
11-10 の 2 日で」を書かない。原因の見出しは日付ではなく出来事にする。日付を出すのは、決算や
報道のように出典の日を示すときだけ。銘柄の日ごとの株価の表も作らない。

**「出し方」の節に手順を書き写さない。** [`methods/weekly-market-v3.md`](../../../kessannote/methods/weekly-market-v3.md)
に書いてある。本文にはその週に固有の値だけ置く。期間、母集団の件数、いつもと違うことを
したときの断り。テーブル名と SQL のファイル名は書かない。

定義を変えて数字が動いたら、版を上げて `methods/weekly-market-v4.md` を作る。既存の版は
書き換えない。古いレポートが古い版を指したままになるように。

分からなかったことは `## 未確定` に残す。`/open/` が全レポートから拾う。

### 7. 建てて commit し、push する

```bash
cd kessannote && npx astro build && npx astro check
```

commit は `kessannote` で行い、そのまま push する。レポートと SQL を同じコミットに入れる。

```bash
cd kessannote && git push origin main
```

ユーザはサイトでレポートを読む。push しないと読めない。ここから質問の往復が始まり、
レポートが何度か変わる。そのたびに commit して push する。

## ここからが本番

レポートを出したら終わりではない。ユーザが読んで、銘柄や「未確定」について質問してくる。
**そこで調べた結果は、会話で答えて終わりにせず、必ずレポートに書き戻すこと。** 書き戻さ
ないと、次に同じ問いが来たときにまた調べ直すことになる。

### 8. 質問に答えて追記する

1 問ごとにこの順で回す。

1. **DB を先に引く。** 適時開示、決算、値動きの日別。答えが DB にあることは多い
2. 足りなければ Web を引く。記事は開いて日付と中身を確かめる
3. 数字が食い違ったら、その銘柄だけ取得元から取り直して照合する。レポートには「開示資料と
   照合した」「東証の終値と照合した」と書き、取り直したことは書かない
4. レポートに節を足す。出典のリンクを必ず付ける
5. 建て直して commit し、push する

会話の返答とレポートの中身を揃えること。会話では書いたのにレポートに無い、が一番まずい。

### 9. 未確定を動かす

質問で解けたものは「未確定」から外す。**代わりに、掘ってみて新しく出てきた問いを足す。**
未確定は減らすものではなく、入れ替わるもの。

部分的にしか解けなかったときは、消さずに文を書き換える。何が分かって何が残っているかを
書く。JPX の更新日は観測が 3 点に増えても特定できなかったので、「観測は 3 点に増えた。
ただし拡張子の変更と重なって切り分けられない」に書き換えた。

`date` は動かさない。同じ日の追記なら作成日のままでよい。日をまたいで大きく書き足した
ときだけ、最終更新日に寄せる。`summary` は結論が変わったら直す。

`kabu-app` や `kabu-terminal` に触っていれば、それぞれ別に commit して、そのまま push する。

## つまずきどころ

**SQL を直したら、前と同じ数字が出るか照らすこと。** 動くかどうかだけ見ても足りない。
単位を十億と億で混ぜていたのを、全体の売買代金と突き合わせて見つけたことがある。

**検索結果の要約は数字がずれる。** ソフトバンクグループの 09-04 終値を「5,001 円」とする
要約が出たことがある。実際は 5,590 円だった。値は必ず `ticks` を正とする。

**記事の配信時刻を見る。** 前場引け (12:37 など) の記事は大引けと値が違う。09-07 の記事は
SBG を 6,052 円としているが、大引けは 6,217 円だった。食い違いに見えたら、まず時刻を疑う。

**出来高が少ない日を「動いていない」と読まない。** ストップ高やストップ安に張り付くと商いが
細る。ティアフォーは 08-31 に 194 万株で +20% 上げた。前後は 3,800 万株と 8,000 万株ある。

**指数が上げた日に中央値が動いていないことがある。** 09-07 は日経平均が前場で 2% 以上上げた
一方、中央値は 0.00% だった。値がさ 2 銘柄が指数を押し上げただけで、地合いは重かった。
等加重で見る意味がここに出るので、乖離を見つけたら書くこと。

**指数は持っていない。** 日経平均も TOPIX も Yahoo から取れない。手元の `ticks` から等加重で
作る。日経平均の騰落に触れるときは、必ず出典を付ける。
